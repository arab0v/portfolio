Shipping Rezefy in Under 3 Months With 3 Technical People

2026-09-24 · ai-workflow, nestjs, adminjs, keycloak

Spent weeks evaluating admin frameworks before picking anything. AdminJS was the closest fit — not because it covers everything, but because it doesn't get in the way of the 20% it doesn't cover.

TL;DR — Weeks evaluating AdminJS, then fixed its v7/ESM clash with NestJS before NestJS itself shipped ESM. Auth locked down (3-layer RBAC + Keycloak, Redis sessions, kill-everywhere) before one admin screen existed. Shipped all of Rezefy — platform + admin portal — in under 3 months, 3 technical people, running the agent across 125 sessions and roughly 17.5k of my own prompts. Every mistake it made got written into a skill file so the next session didn't repeat it.

The first real fight

First real fight with it had nothing to do with our admin flows: AdminJS v7 went full ESM while NestJS was still CommonJS-only (v12 hadn't landed ESM support yet), and the "official" example everyone links to doesn't even run. Wrote up the fix — dynamic import() confined to one loader file, rest of the app stays CommonJS — before NestJS's own team shipped ESM support: AdminJS v7 in Classic NestJS Without Tears.

Startup constraints

We're a startup: 3 technical, 1 backend, 1 frontend, and our CTO. rezefy.com and landlord.rezefy.com are the same platform serving two different user types with genuinely complex flows. We don't have the headcount to hand-customize every button in an internal admin panel — so the first and only non-negotiable was auth. Get that right, keep the CRUDs simple, and don't burn our two engineers polishing a tool only five people use.

Auth first

Three-layer RBAC against Keycloak, Redis-backed sessions so a restart doesn't log everyone out, kill-session-everywhere for when someone needs to be locked out fast. Tested that hard before touching anything else, because a broken CRUD is an inconvenience and a broken auth check is not.

Weeks of alignment, not code

After auth was solid, I spent weeks — not writing code, talking. To our administrators, and to the AI agent, back and forth, aligning on what the admin experience actually needed to be. Not what I assumed they wanted.

New team, new everything, and we shipped all of Rezefy — the platform and the admin portal — to production in under 3 months. That was a milestone for us, and AI carried a real share of it. Pulling the raw agent logs for the admin app alone: 125 sessions since late August, ~17.5k prompts from me, 16k+ tool calls, 397 commits touching just rezefy-admin (60 of those in the last month), 23k lines added and 7.5k removed in that stretch. 23 resources registered, 94 components wired into the loader, ~68k lines of admin code total.

Where I kept control

My job was making sure the agent adapted to how I write NestJS — the server side stayed disciplined, my patterns, my review. Frontend I gave it more room to do what it does best.

The challenges — where AI actually struggled

Not a clean story. 87 of those sessions got interrupted mid-task — me stopping it because it went sideways, guessed at a field name instead of asking, or built something in the wrong direction entirely. Recurring failure modes worth naming:

  • Same bug shape kept resurfacing across different resources — a "record" action handler returning a hand-rolled object instead of calling record.toJSON(currentAdmin). Fixed it, moved to the next resource, agent reintroduced the identical bug three more times before it stuck.
  • Component registration is a two-file requirement (dev loader + prod bundler) — the agent forgot the second file constantly, which meant "works in dev, breaks in prod" surprises.
  • Padding/layout regressions repeated across 9 separate show pages — same one-line mismatch every time (a header-visibility flag changing what padding the component needed to supply itself).

None of that got fixed by a better prompt in the moment. It got fixed by writing the failure and its correct pattern into a persistent skill file the moment I caught it — not as a note to myself, as a rule the next session reads before it touches the code. That skill file is now 604 lines across 16 sections. Early sessions, before the skill existed, were rough — lots of re-explaining the same constraints. By the last few weeks the pattern mostly held on the first pass, because the rule was already there instead of living in my memory.

Where we are now

Now we ship straight from a Jira ticket to the agent. We still review. We still QA before it goes out. But the gap between "ticket exists" and "code exists" isn't where our time goes anymore.
